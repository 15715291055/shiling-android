# 编译、真机验证、升级与交付

## 先构建，再判断是什么问题

优先使用工程 Wrapper 和已有脚本。在项目根运行适合当前模块的任务，例如常见 `app` 模块在 Windows 下的 Debug 构建：

```powershell
.\gradlew.bat :app:assembleDebug --console=plain
```

模块名与任务以工程实际配置为准。首次运行可能需要下载 Wrapper 和依赖；缓存与临时目录遵循用户存储要求，`local.properties` 的 SDK 路径不能提交。

| 症状 | 下一步 |
| --- | --- |
| Java/Gradle 启动失败 | 对照 AGP/Wrapper 所需 JDK，检查实际执行的 Java |
| 发行包或依赖下载失败 | 检查网络、仓库、校验值及本机既有代理；不关闭 TLS 校验 |
| SDK/许可证/Build Tools 缺失 | 安装所需官方组件，接受条款时遵循环境授权流程 |
| Kotlin/Compose/KSP 编译失败 | 读取第一处实质错误，确认插件兼容与生成代码问题 |
| AAPT/资源/Manifest 合并失败 | 检查出错资源、命名空间、依赖 Manifest 与合并报告 |
| 签名或安装失败 | 检查包名、versionCode、证书及安装目标用户，不先卸载 |

每轮保留实际退出码与关键日志。不要重复同一失败命令期待不同结果，也不要把历史成功构建日志当成本次结果。

## 按风险选择验证

编译通过后执行与改动相称的 lint、纯逻辑测试或设备测试。数据库迁移与备份需要检查字段和资源；分享分页需要检查完整内容；手势需要长文和方向变化。静态色板、说明文案不需要为了数字增加重复测试。

示例任务（按工程需要选择）：

```powershell
.\gradlew.bat :app:lintDebug --console=plain
.\gradlew.bat :app:assembleDebugAndroidTest --console=plain
```

运行设备测试前：

1. 以 `adb devices -l` 确认授权设备。多设备显式选择 serial。
2. 确认 Android 用户/工作资料与目标包，不能认为设备上只有 user 0。
3. 核实测试包与正式包隔离；测试包也可能有用户试写数据，不能默认可清空。
4. 在隔离环境运行会清理或改写数据的测试；已有需保留的数据先备份。
5. 安装后检查目标用户下的实际版本、启动和关键流程，不能只看安装输出 Success。

核心真机流程按产品选取：新增/修改/删除与取消、重启持久化、长文滚动和输入法、图片选择与放大、分享生成后预览/保存、权限拒绝、离线状态、备份导出与恢复。

没有真机时可在模拟器验证并如实标记，不能把模拟器结果写成某款手机实测。不要为演示而修改正式应用里的用户偏好、日记或足迹。

## 已有用户的安全升级

升级前记录包名、版本、数据库版本和公开签名证书指纹；通过应用正常备份或获授权的受支持方式取得完整恢复点。不要为了导出正式数据而 root 手机或绕过私有目录隔离。

核对维度：

- 按稳定 ID 比较完整结构化字段，忽略的易变字段需解释。
- 对照片等二进制资源比较 SHA-256，确认引用可解析。
- 检查关联实体、心情/标签历史快照、设置和附件，按实际 schema 选择。
- 新增、删除或迁移导致的预期差异单独列出。记录数量相等不能证明内容相等。

用户还在操作应用时，前后两份备份可能包含正常新增内容；不要为了“对账一致”覆盖新记录。若导出助手发现用户在编辑、颜色选择或其他非预期页面，应停止该自动化并保留现场，不强行关闭或丢弃草稿。

正式版使用原签名、原应用 ID 与递增 versionCode 覆盖安装。升级后再导出并核对。用户不要求迁移测试记录时，保持两个包的数据独立。检查无法完成就明确写未验证，不沿用上一版本的通过结论。

## APK 签名与交付

Debug APK 通常由测试密钥签名，不能充当承诺的正式版。Release 构建是否已经签名取决于工程配置；检查实际文件而非只看文件名。

已有正式项目缺少原密钥时，停止生成升级包并恢复原签名材料，不能静默新建密钥。新项目首次发布可以建立独立发布密钥并安全保管；口令不写进代码、命令日志或 Git。

沿用工程签名配置，或使用 SDK 的 zipalign/apksigner 工具。确认对齐发生在签名前，并执行签名验证；使用 [Android 官方签名说明](https://developer.android.com/studio/publish/app-signing) 处理当前发行方式。Play App Signing 的上传密钥与最终分发签名可能不同，不可混淆。

最后记录：APK 实际路径、大小、SHA-256、包名、版本、签名验证、测试范围和安装状态。Source ZIP、未签名产物、安装成功与数据保留是不同的结果。

## 可选：发布源码与 Release

只有用户要求发布时才执行。确认目标账户、仓库与可见性，沿用用户选择；需要暂存且未指定公开时，优先私有，不能把“上传 GitHub”解释成允许公开私人数据。

构建源码与本机状态分开：排除签名密钥/口令、令牌、`.env`、本机 SDK 路径、数据库、真实照片、设备私有备份、缓存以及含私人内容的截图/录屏。`.gitignore` 不能移除已经跟踪的文件，必须检查实际暂存树和提交历史。可共享的设计图使用合成素材。

优先现有可用的 GitHub 能力；没有时可使用官方 `gh` 与正常网页设备授权。不请求用户发送原始令牌或密码。若命令行无法联网而系统浏览器正常，检查该进程是否继承了本机既有代理；不改系统安全设置，不提交代理凭证。

提交前查看实际文件列表与凭证模式扫描结果。先推送源码，再按需要创建与源码提交对应的版本标签和 Release。上传已验证 APK 与校验文件，使用 GitHub 返回的文件大小/摘要核对；不要额外上传未经审查的历史源码 ZIP 或私有交接文档。

已有远端时先读取状态，避免覆盖其他改动。发布失败保留本地成果和明确阻塞，不把“创建了仓库”写成“源码与 APK 都已发布”。
